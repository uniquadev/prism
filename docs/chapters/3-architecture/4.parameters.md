# 3.3 Parameters and configuration

The current sources separate three kinds of values. Protocol constants live in
`repo/prism-hdl/src/prism_pkg.sv`; developer-selectable build defaults live in
`prism_build_config_pkg.sv`; CONTROL installs runtime state. Derived values are
computed rather than transmitted or configured twice.

## Protocol constants

These values define the wire ABI and are not arbitrary module parameters:

| Constant | Value |
|---|---:|
| Protocol version | 1.0 |
| EtherType | `0x88B5` |
| Ethernet payload MTU | 1500 bytes |
| Control word | 2 bytes |
| CONTROL/DATA/RES class header | 24 bytes |
| PROGRESS header | 40 bytes |
| Maximum DATA/RES numeric payload | 1474 bytes |
| Chunk Index | 24 bits |

Changing one of these values is a protocol change and requires matching updates
to the CCL, RTL, tests, PCAP parser, and Wireshark dissector.

## Throughput sizing

For datatype \(d\), let \(b_d\) be its wire bits per element, \(L_d\) the
physical lanes, \(f\) the clock, and \(II_d\) the initiation interval:

\[
T_d = \frac{L_d b_d f}{II_d}, \qquad
L_{min}(d)=\left\lceil\frac{T_{goal}II_d}{b_df}\right\rceil, \qquad
L_{bus}(d)=\frac{D}{b_d}.
\]

For \(D=512\), \(f=250\,\mathrm{MHz}\), \(II=1\), and
\(T_{goal}=100\,\mathrm{Gbit/s}\):

| Input | Minimum lanes for 100 Gbit/s | Lanes per full beat | Current 16-lane rate |
|---|---:|---:|---:|
| FP32 | 13 | 16 | 128 Gbit/s |
| FP16/BF16 | 25 | 32 | 64 Gbit/s |
| INT8 | 50 | 64 | 32 Gbit/s |

`LANES=16` currently sets both tile size and issue width for every format. Only
FP32 meets the target. Narrow formats eventually backpressure because unpacking
does not create more physical lanes.

For \(N\) simultaneous contributors, an aligned binary reduction requires:

\[
E_{input}=NL_d, \qquad A_{binary}=(N-1)L_d.
\]

Kulisch instead accepts \(NL_d\) deposits. Both paths output \(L_d\) reduced
elements. A wider output type can then become the bottleneck:

\[
P_{e2e} \le
\min\left(P_{in},\left\lfloor\frac{D}{b_o}\right\rfloor\right).
\]

For example, 64 INT8 inputs converted to FP32 need 2048 output bits per cycle.
One 512-bit egress must serialize or backpressure them. The rates above describe
numeric payload, not Ethernet overhead or timing closure.

### Logical tiles and physical issue width

A scalable build should separate:

- `TILE_ELEMENTS`: logical elements per microtile;
- FP32 issue slices;
- Kulisch issue slices for each compiled width.

Keeping `TILE_ELEMENTS=16`, one 512-bit beat corresponds to one FP32 microtile,
two FP16/BF16 microtiles, or four INT8 microtiles. It therefore requires 1, 2,
or 4 issue slices. This separation is proposed, not implemented.

### Kulisch width and cost

The compiled widths are 64, 288, and 320 bits. The selector chooses the smallest
one covering:

\[
W=E_{max}-E_{min}+p+1+\lceil\log_2(\text{maximum terms})\rceil.
\]

If none is sufficient, the largest is used with `ACCUMULATION_INEXACT`; saturation
prevents wrap. The current RTL has 16 FP32 and Kulisch lanes. Every Kulisch lane
is stored at the maximum width, so 64/288/320 select numeric capacity, not
independent lane banks.

Its approximate state cost is:

\[
S_{Kulisch} \approx B R_b L_K W_K.
\]

Here \(B\) is the arithmetic-bank count, \(R_b\) the range contexts per bank,
\(L_K\) the lane count, and \(W_K\) the stored width. Kulisch issue width should
therefore be independently configurable.

## Runtime configuration

CONTROL commands install or select:

- session ownership/cookie and lease information;
- node role and group lifecycle;
- Contributor ID, ingress port, source MAC, and endpoint/child binding;
- result route ranges and replication destinations;
- collective semantic (`REDUCE` or `ALLREDUCE`) and `SUM` operator;
- input, accumulator, partial, and output format tuple;
- element count, maximum reduction terms, requested window/replay values, and
  timeout/retry policy fields;
- operation generation and active/prepared/complete lifecycle.

The first RTL integration uses one `SINGLE` node and two endpoint contributors.
Roles and reliability fields present in the protocol do not establish a
multi-switch or replay datapath in this implementation.

## Derived values

Examples include:

- `KEEP_W=DATA_W/8`;
- pointer width and occupancy width from FIFO depth;
- elements per chunk from payload bytes and datatype size;
- chunk count from element count;
- global first element from stream-local Chunk Index;
- maximum frame beats `ceil((14+1500)/(DATA_W/8))`;
- required/selected Kulisch width and bank index.

The functions in `prism_pkg.sv` are the RTL authority for byte size, chunk
geometry, safe logarithms, Kulisch width, and contiguous `tkeep`. The CCL has
matching canonical calculations and its unit tests check the wire model.

## Elaboration checks and verification

Modules use `$fatal` guards for illegal combinations such as non-byte AXI
widths, zero capacities, a parser width smaller than the fixed prefix, invalid
port indices, or an invalid width set. The parameter suite elaborates the full
top with 1, 2, and 4 ports and varied FIFO/context/lane/Kulisch settings. These
checks prove that selected configurations elaborate; synthesis resource use and
timing must still be measured for each deployment profile.
